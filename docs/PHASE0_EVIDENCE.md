# Phase 0 evidence record

This record captures the reproducible Qwen3x-Orin bootstrap state on
**2026-07-18 (Asia/Shanghai)**. It is an engineering milestone, not an
end-to-end model support claim.

## Target environment

- Host: Jetson AGX Orin, aarch64, Linux `6.8.12-1021-tegra`.
- NVIDIA userspace: L4T R39.2.0.
- Device: compute capability 8.7, 16 SMs, 61.40 GiB unified memory.
- CUDA driver/runtime: 13.2 / 13.3; `nvcc` 13.3.
- Build tools: CMake 3.28.3 and GCC 13.3.0.
- Build contract: C++17/CUDA 17, Release, `Q3X_CUDA_ARCHITECTURES=87`.

The device probe reported optimized `sm_87`, unified addressing and managed
memory support, then completed a CUDA smoke kernel.

## Reproduction

```bash
cmake -S . -B /tmp/q3x-orin-phase0 \
  -DCMAKE_BUILD_TYPE=Release \
  -DBUILD_TESTING=ON \
  -DQ3X_CUDA_ARCHITECTURES=87
cmake --build /tmp/q3x-orin-phase0 -j
ctest --test-dir /tmp/q3x-orin-phase0 --output-on-failure
/tmp/q3x-orin-phase0/qwen3x-orin probe
```

The milestone run passed all nine tests:

1. CUDA device classification and smoke probe;
2. NVFP4 CPU/CUDA reference agreement;
3. FP8 CPU/CUDA reference agreement;
4. model descriptor and checked-derived-dimension validation;
5. strict pinned checkpoint/ModelOpt metadata validation;
6. SHA-256 known vectors and streaming behavior;
7. bounded strict JSON parsing;
8. bounded safetensors header/index parsing;
9. inspector CLI discovery.

## Independent end-to-end oracle

The complete pinned 27B checkpoint was loaded on this Jetson AGX Orin by vLLM
`0.23.1rc1.dev269+gccd49f682` in text-only eager mode. vLLM resolved the
checkpoint as `modelopt_mixed`, selected the SM87-compatible Marlin W8A16 path
for FP8 projections and Marlin W4A16 for NVFP4 projections, and consumed
19.12 GiB for model weights after loading. The run used BF16 activations and an
FP8 E4M3 KV cache.

For the fixed no-thinking chat prompt “用一句话解释 CUDA 是什么。”, two sequential
greedy runs in one initialized engine produced the same 26 output token IDs,
decoded text, and reported chosen-token log probabilities. Generation ended
normally at `<|im_end|>` rather than at the length bound. The normalized
[greedy fixture](../tests/fixtures/qwen36-27b-nvfp4-greedy.json) records the
full model identities, environment, engine/sampling parameters, exact input
and output tokens, per-token log probabilities, comparison tolerances, and
non-normative timings. The corresponding
[reproduction utility](../tools/reference/qwen36_27b_vllm_greedy.py) bypasses
tokenization by submitting those exact input token IDs and can rehash all four
materialized source files before running.

A second compact [layer-boundary fixture](../tests/fixtures/qwen36-27b-nvfp4-layers.json)
records the final prefill position and first recurrent decode position at the
embedding, all 64 `(hidden, residual)` decoder boundaries, final normalization,
and top logits. It contains hashes, statistics, and fixed samples rather than
full activation dumps, and is regenerated by
[`qwen36_27b_vllm_layers.py`](../tools/reference/qwen36_27b_vllm_layers.py).

The cache policy was then made explicit instead of relying on vLLM `auto`:
full-attention KV, causal-conv history, and DeltaNet state were all forced to
BF16, matching the native correctness baseline. The same 26 greedy token IDs,
decoded text, and stop token were reproduced; only the diagnostic log
probabilities moved slightly. The normalized
[BF16 greedy fixture](../tests/fixtures/qwen36-27b-nvfp4-greedy-bf16.json)
has SHA-256
`5945e9420be59395644e3c613954f7cdb3d3121f69a42f58b8516011b340c454`.
The corresponding 64-layer
[BF16 boundary fixture](../tests/fixtures/qwen36-27b-nvfp4-layers-bf16.json)
has SHA-256
`581a487f315dbc2fa2f70ce6cf8c130549ea04dbf1144a1861e5683f5c18df61`.
Both reproduction utilities now pass recorded cache dtypes explicitly and
accept controlled dtype overrides.

## Native reference-generation follow-on

The Phase 2 native path subsequently completed the same pinned prompt on this
Orin. This is recorded here to connect the original Phase 0/vLLM oracle to its
native consumer; it does not retroactively change the nine-test Phase 0
milestone above.

```bash
qwen3x-orin generate MODEL_DIR \
  --prompt "用一句话解释 CUDA 是什么。" \
  --max-tokens 26 --trace
```

The pinned tokenizer produced the fixture's exact 19 prompt IDs. The native
runner completed 44 sequential steps, produced the fixture's exact 26 output
IDs including terminal `248046`, reported `stop_reason=im_end`, and decoded
the exact expected text:

> CUDA 是 NVIDIA 开发的一种并行计算平台和编程模型，旨在利用 GPU
> 的强大算力来加速通用计算任务。

The one-run, non-normative measurements were:

| Measurement | Observed value |
| --- | ---: |
| Cold load total | 213,845.054 ms |
| Authenticated resident load | 212,683.392 ms |
| Request arena | 82,505,216 bytes |
| Prompt prefill / TTFT | 20,559.187 ms |
| Decode after first token | 28,652.488 ms |
| Total generation | 49,211.675 ms |
| Mean later-token step | approximately 1,146.100 ms |

Trace capture retained embedding, all 64 hidden/residual pairs, final norm,
and full-block SHA-256 for every step. The two fixture localization positions
had these native summaries:

| Position | Full trace SHA-256 | Final-norm SHA-256 |
| ---: | --- | --- |
| 18 | `a780bede09bb74be107323444ec2be4b2165c89721624025308525c31c1dc226` | `1b4edfc36c9dea31414dc8a1668c8ad10cad9e574ff32871a18c8e0d28131b7b` |
| 19 | `76b767786fa92b117833e79062aab1e4ea8942e0c61ac8fd7b6840744fbc85f1` | `266c82ecdd4df8e7b3aad8e4de7a78b8c622e3f15129bbfda24bc0c85a23f680` |

Those native boundary hashes are not bitwise-equal to the vLLM BF16 fixture.
This is expected for this cross-backend diagnostic: the native path preserves
each checkpoint projection's independent ModelOpt scale whereas vLLM
requantizes fused projection operands, and the native sequential prefill
updates BF16 GDN state token by token whereas vLLM uses chunk prefill. The
intermediate rounding/order therefore differs even though generated IDs,
decoded text, and the stop decision match exactly. Boundary samples and
tolerances—not cross-backend hash equality—remain the localization policy.

## Phase boundary

The Qwen3.6 portion of Phase 0 is reproducible: build/device gates, exact
metadata identities, fail-closed compatibility, and checkpoint-derived kernel
shapes are checked in. Qwen3.5 architecture descriptors remain targets, but no
Qwen3.5 ModelOpt artifact is claimed from shape compatibility alone.

Phase 1 direct loading is complete. Header/index parsing, strict all-shard
ownership and payload validation, ModelOpt dispatch metadata, and the
NVFP4/FP8/BF16 GEMV references are complete. The authenticated direct loader
has also reproduced a single
20,150,786,560-byte text arena from all three official shards in 212.736 seconds
while matching every full-file SHA; see
[RESIDENT_WEIGHT_LOADER.md](RESIDENT_WEIGHT_LOADER.md). Remaining Phase 1 work
is the lossless repack path and versioned `.q3x` cache. The end-to-end oracle
above now has a native Phase 2 consumer: the strict 64-layer weight binding,
allocation-free mixed-precision projection dispatch, bounded request state,
hybrid runner, tokenizer/chat layer, greedy controller, and CLI reproduce its
fixed-prompt tokens and text exactly. Broader repeatability and tolerance-based
cross-backend boundary characterization remain active correctness gates.
