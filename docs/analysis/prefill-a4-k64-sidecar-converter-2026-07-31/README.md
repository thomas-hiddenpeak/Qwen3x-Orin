# Full-model A4-K64 sidecar conversion contract

Date: 2026-07-31
Scope: pinned `Qwen3.6-27B-NVFP4`, all 400 Prefill projections
Status: host converter and production admission contract; no real 12 GB
sidecar was generated by the test suite

## Decision

`qwen3x-a4-sidecar` is the only production conversion entry point. It reuses
`build_qwen36_27b_prefill_sidecar_manifest()` and therefore inherits the exact
ordered 400-projection inventory, source-component digests, shapes, K64 byte
budget, and 256-byte offsets. It never infers calibration values and never
loads a complete source matrix into memory.

Production conversion requires:

1. the exact pinned config, quant config, index, shard headers, shard sizes,
   and full-shard SHA-256 identities;
2. one version-1.0 policy record for every ordered manifest entry;
3. exact checkpoint/config/index/manifest and per-projection source-SHA
   bindings;
4. explicit weight and activation clip ratios, activation K64 grouping, and
   rounding policy;
5. a temporary complete payload, on-disk size/SHA verification, `fsync`, and
   no-replace atomic publication.

The synthetic nearest-even helper exists only for small correctness and I/O
tests. Its mode is `experimental_nearest_even_smoke`; a receipt carrying that
mode is rejected before the payload can enter production residency.

## SM87 consumer-prepacked payload ABI

Each manifest entry begins at its fixed 256-byte-aligned `sidecar_offset` and
contains exactly:

```text
signed W4 weights: uint8 [N/64][K/64][64][32]
BF16 weight scales: uint8 [N/64][K/64][64][2]
```

Let `NB=N/64`, `KB=K/64`, and `n=nb*64+local_n`. The exact byte
addresses, relative to the start of the sidecar file, are:

```text
weight(nb,kb,local_n,pair) = sidecar_offset
  + (((nb * KB + kb) * 64 + local_n) * 32 + pair)

scale(nb,kb,local_n,byte) = sidecar_offset + weight_bytes
  + (((nb * KB + kb) * 64 + local_n) * 2 + byte)

weight_bytes = N * K / 2
scale_bytes  = N * K / 64 * 2 = N * K / 32
entry_bytes  = weight_bytes + scale_bytes
```

`pair` is `local_k/2` in `[0,31]`; the byte's low nibble is even `local_k`
and its high nibble is odd `local_k`. Scale `byte=0` is the low BF16 byte and
`byte=1` the high byte. Entry alignment gaps in the arena carry no data and
remain zero. The fixed physical-layout identifier is
`sm87_s4_n64_k64_consumer_v1`.

N64 is the physical/fundamental B consumer block, not a fixed CTA tile. A
kernel may combine adjacent blocks; for example M32N128 consumes two adjacent
N64 blocks and issues two contiguous 2 KiB B loads per K64 stage. The layout
does not lock the scheduler to M64N64.

The matching dynamic activation ABI is symmetric:

```text
signed A4 activations: uint8 [M/64][K/64][64][32]
BF16 activation scales: uint8 [M/64][K/64][64][2]
```

M64 is likewise the physical A block rather than a required CTA M tile; an
M32 CTA may consume the upper or lower half of an M64 block.

- signed codes use `[-7, 7]`;
- codes are four-bit two's-complement;
- even K occupies the low nibble and odd K the high nibble;
- scales are BF16, little-endian;
- every K64 group uses
  `threshold=max(abs(group))*weight_clip_ratio` and
  `scale=BF16(threshold/7)`;
- rounding is deterministic nearest-even version 1.

All fixed model N and K dimensions are divisible by 64. Weight and scale byte
counts therefore remain exactly the manifest's original A4-K64 budget; only
the physical order changes. There is no per-entry payload metadata
(`metadata_bytes == 0`). Calibration is
a source-bound companion policy, and its exact byte length and SHA-256 are
bound by the publication receipt.

## Calibration policy ABI v1.0

The JSON parser uses an exact-field schema: missing and unknown fields fail.
Duplicate fields already fail in the bounded JSON parser. The root is:

```json
{
  "schema": "q3x.prefill.a4.calibration-policy",
  "version": {"major": 1, "minor": 0},
  "mode": "production_calibrated",
  "sidecar_kind": "a4_k64",
  "physical_layout": "sm87_s4_n64_k64_consumer_v1",
  "source_checkpoint_id": "<pinned id>",
  "source_config_sha256": "<hex64>",
  "source_index_sha256": "<hex64>",
  "manifest_sha256": "<hex64>",
  "projections": ["exactly 400 ordered records"]
}
```

Every projection record is:

```json
{
  "ordinal": 0,
  "source_module": "model.language_model.layers.0.mlp.gate_proj",
  "source_sha256": "<manifest entry hex64>",
  "weight_clip_ratio": 0.9375,
  "activation_clip_ratio": 0.96875,
  "activation_scale_group_size": 64,
  "rounding": "nearest_even_v1",
  "channel_equalization": null
}
```

Both clip ratios must be finite and in `[1/256,1]`. The lower bound is part of
v1 and prevents a nominally positive double from becoming a zero float/BF16
threshold. The runner must use
`activation_clip_ratio` when it dynamically quantizes each activation K64
group; it must not hard-code `1.0`. The runtime parser/validator in
`prefill_a4_sidecar_converter.h` is the ABI authority.

Records that consume the same activation repeat the metadata but are required
to agree exactly. The validator groups Gate+Up, linear QKV+Z, and full Q+K+V
within each layer and rejects any disagreement in activation clip, group size,
rounding, or channel equalization. Down and each O projection have independent
input boundaries. In particular, the Gate+Up producer uses the Down record's
`activation_clip_ratio` when it emits the A4 intermediate consumed by Down.

Optional channel equalization is explicit:

```json
"channel_equalization": {
  "scheme": "input_channel_multiply_f32_v1",
  "factors_path": "calibration/layer0-gate.f32",
  "factors_sha256": "<hex64>",
  "factor_count": 5120
}
```

The factor payload is little-endian FP32 `[K]`, with finite positive values.
The defined transform is
`equalized_weight[n,k] = weight[n,k] * factor[k]`, while the runner must apply
the inverse factor to the matching activation. Factor paths are safe relative
paths resolved against the supplied policy location, and the schema binds the
exact file size and SHA. The v1 parser retains this metadata, but the current
production converter rejects any non-null equalization record before opening
or converting the large checkpoint shards; residency rejects it again as
defense in depth. This avoids publishing a 12.9 GB artifact that the current
runner cannot consume correctly.

## Source decoding and bounded memory

For each N64 row chunk (default 64 rows, optionally a small multiple):

- NVFP4 is decoded as
  `E2M1(code) * E4M3FN(block_scale) * weight_scale_2`;
- FP8 is decoded as `E4M3FN(code) * weight_scale`;
- optional equalization decoding is implemented but production conversion is
  gated off until the runner supports authenticated inverse factors;
- W4 and BF16 scale chunks are written directly in consumer tile order.

The largest ordinary work buffer is proportional to `row_chunk_size * K`,
not `N * K`. The converter authenticates and retains open file descriptors for
the three real checkpoint shards under shared locks. It compares inode/size/
mtime/ctime snapshots and complete pinned SHA-256 both before and after
conversion, catching ordinary in-place modification and restoration. It does
not map or retain all matrices and does not call CUDA.

## Publication and residency

Successful conversion publishes:

```text
OUTPUT
OUTPUT.receipt.json
```

The receipt records schema/version, production eligibility, checkpoint/config/
index/manifest SHA bindings, mandatory
`physical_layout=sm87_s4_n64_k64_consumer_v1`, exact policy byte length/SHA,
payload byte
length/SHA, and projection count. Existing output or receipt paths cause a
failure; they are never replaced. The payload link is created before the
receipt link, so a crash can leave an unavailable orphan payload but can never
make an incomplete payload admissible.

The physical-layout identifier is covered by the exact policy SHA and repeated
in the publication receipt. A legacy canonical row-major A4 payload is rejected
even if it carries the same v1 manifest kind and manifest SHA. This converter
does not attach the artifact to the default production path by itself: the
runner and GEMM consumer must first use this N64/K64 prepacked ABI and consume
the authenticated held file descriptor.

Temporary files use unpredictable `mkstemp` names with exclusive creation;
the converter never removes a guessed/pre-existing temporary path. Payload and
receipt are switched read-only before no-replace hard-link publication. A
post-link cleanup or directory-sync failure rolls both final links back.

`production_residency_eligible` means that the artifact is authenticated and
conforms to this ABI. It does **not** assert model accuracy or calibration
quality. Capability admission must separately approve the bound policy SHA and
real-model evaluation evidence; the converter cannot turn a self-labelled
policy into an accuracy verdict.

Production loading must call
`authenticate_prefill_a4_publication_for_residency()` with the rebuilt
manifest, receipt, payload, and original policy path. There is no digest bypass.
The gate reparses and revalidates all 400 policy records, checks policy
bytes/SHA against the receipt, rejects experimental mode and (for the initial
runner) non-null equalization, then hashes the complete read-only payload. It
returns a `PrefillA4AuthenticatedPublication` holding both the validated policy
and the same locked payload fd. The runner must consume that fd rather than
reopening the path, and must call `revalidate_unchanged_after_consumption()`
before exposing residency.

## Command

```bash
qwen3x-a4-sidecar convert \
  /path/to/Qwen3.6-27B-NVFP4 \
  /path/to/calibration-policy.json \
  /path/to/qwen36-prefill-a4-k64.bin
```

`--row-chunk N` changes only bounded CPU working memory and must be a multiple
of 64. `--no-preallocate`
is available for controlled environments, while preallocation is the default
so disk exhaustion fails before the long conversion begins.

## Host verification

`prefill_a4_sidecar_converter` covers:

- valid ordered 400-record policy parsing;
- missing projection and source-SHA rejection;
- optional equalization metadata validation;
- experimental receipt rejection before residency;
- exact consumer-tile order, signed-nibble packing, nearest-even ties, and
  BF16 little-endian scales;
- an aligned binary I/O round trip.

Synthetic values are used only for those correctness/I/O checks. They are not
used for performance admission and the test never creates the 12.923 GB real
sidecar.
